# 验收盲区：错误前提会穿透「自验 + 他验」

> 2026-09-13 复盘。来源：VS-1（G-02 失败重试上限）的真实事故——**我的自测通过、两次独立 Evaluator 也通过，但代码有 P0 缺陷**。

## 事故经过

G-02 的实现意图是"限制**失败重试**次数"。我把它写进了任务卡：
> "失败 attempt 达到上限后不再 claim"

但我在实现时把 `attempt` 理解成了"该 job 的全历史 attempt"（`latest.attempt + 1`），于是实际语义变成：
> **正常任务累计跑满 5 次后，永久不再被调度。**

并且上限判定写在了 `UPDATE last_status='running'` **之后**——命中上限时 job 永久卡在 `running`、没有 run 行，`due_research_jobs` 排除它、`recover_stale_research_runs` 也扫不到 → **定时研究静默死亡，无自愈路径**。

两处都不是笔误，而是**设计层面的错**。

## 为什么自验和他验都没抓到

1. **我的自查**（写测试）：测试是按我自己的（错误）理解写的——我断言"跑满 5 次后 claim 返回 None"，于是测试**为错误行为背书**，全绿。
2. **独立 Evaluator**：任务是"实现是否满足 IMPLEMENTATION_BRIEF"。而 **brief 本身就是错的**（"失败 attempt"这个措辞含糊）。Evaluator 逐条比对了 brief 与代码，结论是"一致"——**它无法质疑 brief 的前提**。
3. **第三方审计（可靠性视角）**才抓出来：它不问"是否满足 brief"，而是问"**系统失败时这条路会怎样**"——于是发现 job 会卡死、正常任务会早死。

## 结论（可迁移的规则）

- **验证的层次**：自验查"我做的对不对"；他验查"是否满足要求"；审计查"**要求本身对不对、系统在最坏情况下会怎样**"。三者不可互相替代。
- **任务卡/brief 是验证的上界**：如果前提有错，所有下游验证都会"一致地正确"。因此**必须有角色去质疑前提**，而不是只检查一致性。
- **审计必须独立于 brief**：审计任务书里不要复述我方的结论或术语（会锚定），只给项目背景 + 代码 + 该视角的检查清单（本项目第一轮四路审计就是这么做的，规则见 `docs/ai/evo/PROJECT_BRIEF.md`）。
- **触发复审的信号**：凡涉及**状态机 / 生命周期 / 重试 / 并发 / 清理**的改动，必须让可靠性视角过一遍——这类缺陷不会体现在"功能测试通过"里。
- **卡片措辞要精确到可判定**："失败 attempt" 这种含糊词应写成"**自上次成功以来连续失败的次数**"。

## 落地动作

- 本轮已修（`eff8e2d` → `d731b57`，复评 ACCEPT）：判定前置、只计 `failed`、限 24h 时间窗自动恢复、手动「立即运行」绕过熔断、文案如实。

## 第二种盲区：含糊的任务书会被"字面实现"（2026-09-13 补充，来源 VS-7）

**事故**：VS-7 卡面写"lead 空内容时 quality 必须与 `report_builder` **同口径**"，并附了 `report_builder.py:368` 的行号。实现者按字面做成 `not lead_content`（判**原始字符串**非空），还写了注释声明"用与 report_builder 相同的真值判定"。但真正的口径在 `:296`——那里先 `lead = parse_lead_review(lead_content)`，判的是**解析出的 dict**。于是"非空但无法解析成 JSON 的散文"（如模型回一句"抱歉，我无法完成本次审核。"）这一情形下，`lead_review_status='degraded'` 而 `quality='audited'`，**卡片声称消除的矛盾依然存在**。

**独立 Evaluator 在 venv 里实测确认**（`parse_lead_review('抱歉…') == {}`），而实现者的自测全绿、注释自洽——因为测试与注释都是照着自己的理解写的。

**可迁移规则**：
- **验收标准必须写成"可判定的谓词"，而不是"与某处一致"**。正确写法：`与 report_builder 使用同一个判定函数 parse_lead_review(lead_content) 的真值`——指名函数，不给解释空间。
- 凡卡片里出现"**同口径 / 保持一致 / 与 X 对齐 / 语义等价**"这类词，要么补上"判定依据（具体函数或表达式）"，要么在验收清单里加一条"**列出两侧的判定表达式并逐字比对**"。
- 引用了行号 ≠ 说清了语义。给 `:368` 只指向了消费点，真正的语义在 `:296` 的生产点。
- 因此 Evaluator 的必查项应包含：**卡片中每处"一致/等价"的声明，都要独立找出两侧的实际判定代码做对比**——这正是本次抓到缺陷的方式。
