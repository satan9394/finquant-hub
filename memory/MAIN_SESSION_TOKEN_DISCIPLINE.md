# 主指挥会话 Token 上限（max-tokens）反复触发的根因与纪律规范

> 经验文件 · 长期记忆 · 创建于上一主会话 session-4fc2a0d7 被截断之后
> 用途：记录"为何子代理执行任务，主指挥会话仍反复触发 max-tokens"的根因，并沉淀后续必须遵守的 token 纪律。

---

## 一、背景（事实依据）

上一个主会话 `session-4fc2a0d7`：

- 总规模：**21175 行 / 16.5 MB** 的 session.jsonl。
- 最后一轮为 **turn 73**，以 `turn/end: reason=max-tokens` 结束，会话在收尾阶段被强制截断。
- 截断造成的直接损失（收尾未完成）：
  - `BACKLOG-042` 代码已写完，但**门禁未复核**；
  - `HANDOFF` / `CHANGELOG` / `EXEC_PLAN` 均**未同步**，状态没有落盘。

即：任务是"做到一半被掐断 → 状态没落盘 → 下个会话要从头 diagnosis / 续查"，这正是 max-tokens 反复触发的第一现场损失。

## 二、量化证据（session.jsonl 按记录类型字节排序，仅列前几）

| 记录类型 | 大致字节 | 备注 |
|---|---|---|
| request / header | ≈ 3,985,676 B | 每条约 132,856 B ≈ 130 KB |
| assistant / chunk | ≈ 2,074,096 B | 模型输出流 |
| tool-call-chunks | ≈ 2,020,920 B | 工具调用片段 |
| tool / result | ≈ 1,932,397 B | 工具返回结果 |
| text-chunks | ≈ 1,713,362 B | 文本分片 |
| assistant / message | ≈ 1,476,470 B | 模型整段消息 |

**关键派生数字**：

- LLM 请求总次数：**30 次 request/header**。即**系统提示词 + 全部约 60 个工具 schema（含 `vision_*`、`workflow`、`subagent` 等超大工具）每 30 次请求各整段重发一遍**，单次约 130 KB（约 3.5–4 万 token 的固定开销）。
- 子代理结果注入主会话：`agent/inbox/spliced` 共 **212 条**；每次研究/收尾/背景任务完成后的整段"工作证明"汇报文本都永久留在主会话。
- 编排类工具调用留在主上下文：`subagent` / `send_message` / `todo_write` / `update_goal` / `agent/inbox` 相关 tool/call 共 **25 次**；每次 `subagent` 的 `prompt` 大段文本、每次 `todo_write` 的整表全量替换都永久留在主会话。
- goal 自动续跑：目标 `objective` 文本在每一轮 `goal_round` 里**整段重复注入**（本会话 goal 目标那段话重复了 **20+ 轮**）。
- 对话历史本身：主会话 **721 条 assistant/message + 111 条真实 user/message**。
- 单轮最大步数：turn 73 有 **68 个 step**，每个 step 一次 LLM 请求，且**把此前全部 tool/result 喂回上下文**。

## 三、根因（核心判断）

### 根因 1：子代理隔离的是"它的"工作上下文，不是"你的"

子代理做事的**细节不会回传**（这是隔离的价值），但它产出的以下内容**全部以 text 永久留在主对话、随轮次累积**：

- 它的**结果汇报**（整段"工作证明"文本）；
- 通过 `send_message` 给你发的**每段 message**；
- 你 `send_message` 给它的**指令**（大段 prompt）；
- 你 `todo_write` 的**整表全量替换**每次都在主会话里重写一遍。

结论：**子代理并没有帮你省掉主会话的累积**，它只省掉了"它的内部推导过程"。凡是进出子代理的文本，最后都沉淀在你的主上下文里。

### 根因 2：最大单项开销不是历史对话，而是"系统提示 + 工具 schema 每请求重发"

- 30 次请求 × ~130 KB 固定开销 ≈ **3.9 MB**。
- 在 16.5 MB 总量里约占**近四分之一**，且**每一轮前沿都在重算**（每步一次 LLM 请求都把这份固定开销重新喂入，600B→800B 的吞吐全部被它挤占）。
- 这是**持续存在、无法靠"少聊几句"减掉**的基线成本，也是最容易忽视的重复累积源头。

### 根因 3：max-tokens 反复触发的真正机制

auto-compact 是**安全网，不是一劳永逸**。只要主会话持续累积（子代理汇报 + 进箱注入 + 编排调用 + goal 文本重复 + 大 tool/result 逗留），超过安全网的压缩能力后就会**周期性顶到阈值被强制截断**，形成恶性循环：

> 累积 → 顶到阈值被掐断 → 状态没落盘 → 下个会话从头诊断 → 又产生新一轮汇报 → 继续累积 …

本次正是 `BACKLOG-042` 收尾时被掐断的典型样本。

### 根因 4：大件逗留

- 大文件 / 大 diff 在主会话里被 read 全文；
- 大 `tool/result`（查询、抓取、长输出）直接留存，没有被裁剪。

这些都直接把主上下文撑大，扩大触发截断的概率。

## 四、纪律规范（后续必须遵守）

给后续主指挥会话的硬性要求，目标是把主会话的累积与"打到一半被掐断"的窗口都压到最小。

1. **子代理只做短证明**：子代理交证约定只回传 `git diff --stat`、关键测试结果、失败摘要这类**短**证明；完整正文写进 `docs/ai/tasks/<卡号>.md` 卡内，主会话只读卡路径、不贴长文。

2. **日志只留指针，证据进文件**：任何"任务日志 / 词记录"类输出，主对话里**只保留"路径 + 一句话摘要 + 工作证明指针"**；全量证据由子代理落盘到文件，主会话不贴长文。

3. **状态先落盘再前进**：每完成一张卡，**先**把卡的状态（`[DONE]` / `[READY]`）、`EXEC_PLAN`、`CHANGELOG`、`HANDOFF` 写盘，**再**做下一步；把"代码写了但状态没记、中途被掐断"的窗口尽可能缩小。

4. **goal objective 保持简短**：目标只写一句话，不要带大段叙事——它会在每一轮 goal_round 里整段重复注入，长目标就是纯浪费。

5. **阶段性收尾点**：攒几张卡就先 `commit` + 复盘一次，制造一个干净的会话断点，避免单会话无限累积下去。

6. **大件不全文进主会话**：大文件 / 大 diff 不要在主会话里 read 全文，改成**切片读取**，或让子代理**先做摘要**再喂入。

## 五、可执行清单（哪些进主会话 / 哪些必须落盘对照）

### ✅ 允许/应留在主会话（小、短、仅指针）

| 事项 | 形态 |
|---|---|
| 子代理工作证明 | 仅 `git diff --stat` / 关键测试结果 / 失败摘要（短） |
| 任务日志 / 词记录 | 仅"路径 + 一句话摘要 + 工作证明指针" |
| todo_write | 尽量精简条目；避免超长描述 |
| 卡状态变更 | `[DONE]`/`[READY]` 一句话 + 卡文件路径 |
| goal objective | 一句话，无叙事 |

### ❌ 禁止进主会话（必须落盘到文件）

| 事项 | 落盘位置 |
|---|---|
| 子代理完整正文 / 大段推理 | `docs/ai/tasks/<卡号>.md` 卡内 |
| 任务日志 / 词记录全量证据 | 独立数据/日志文件 |
| 大文件 / 大 diff 全文 | 不 read 全文；切片或先摘要 |
| 大 tool/result（查询/抓取/长输出） | 裁剪后仅留结论 |

### 🔁 状态落盘的"时机铁律"

每完成一个可验收单位，**立即**依序写盘后再继续：

1. 卡状态（`docs/ai/tasks/<卡号>.md` 的 `[DONE]`/`[READY]`）
2. `docs/ai/EXEC_PLAN.md`
3. `task/CHANGELOG.md`
4. `HANDOFF.md`

---

## 六、一句话总结

> 子代理隔离的是"它的推导"，不是"进出它的文本"；真正的大头是每请求重发的系统提示 + 工具 schema（~130KB × N 次）；auto-compact 只是安全网，治本在于**长文落盘、主会话只留短证明与指针，状态先落盘再前进**。
