# IMPLEMENTATION_BRIEF — Vertical Slice 14：把"疑似过期"从硬退出降级为"警告后照常启动"

> Orchestrator 第五阶段产物，2026-09-13。来源：**R3 审计 A3 的 P1-2**（`PRODUCT_UX_REPORT_R3.md`），**编排者已核实代码事实**。

## 目标
让"预置产物可免 Bun 启动"这条交付承诺**不再被一个脆弱的时间戳判据击穿**：当产物**存在**但被判"过期"而无 Bun 时，**不要直接把用户踢出去**，而是明确警告后**用现有产物启动**；只有产物**确实缺失**时才要求安装 Bun。

## 用户场景
非技术用户下载发行 ZIP（内含 `frontend/dist`），双击 `start.bat`。由于**打包/解压过程可能让 `package.json` 的修改时间晚于 `dist/index.html`**（用户完全不可控），脚本判定"需要重建"；此时若无 Bun，就会走到 `:bun_missing` **直接退出**——用户被要求先去装一个他从未听说过的工具，**而他手里明明有可用的页面产物**。

## 当前问题（已核实）
- 过期判据只有一条：`start.bat:57-63` 比较 `frontend/package.json` 与 `frontend/dist/index.html` 的 `LastWriteTimeUtc`（`:56` 注释自认"只按时间判断"）。
- 判定为"需重建"时进 `:build_frontend`，无 Bun 即 `:69 → :bun_missing → :fail`（`pause` + `exit /b 1`）**硬退出**。
- **两个方向都错**：
  - **假阳性**：重打包触碰 `package.json` ⇒ 产物明明新鲜却被要求装 Bun 并退出（**击穿 VS-8 的交付声明**）；
  - **假阴性**：只改源码不改 `package.json` ⇒ 永远判新鲜 ⇒ **静默跑旧前端**。
- 本卡只处理**假阳性导致的硬退出**（危害更大：用户完全无法使用）；假阴性的缓解见"理想行为④"。

## 理想行为
1. 无 Bun + 产物**缺失** → **维持现状**（给出安装指引并退出；此时无产物可用，退出是正确的）。
2. 无 Bun + 产物**存在但被判过期** → **不再硬退出**：打印**明确警告**（说明"检测到页面产物可能偏旧，将用现有产物启动；如需最新界面请安装 Bun 后重启"）+ **继续启动**。
3. 无 Bun + 产物**存在且判新鲜** → 行为不变（直接复用）。
4. 启动窗口**打印所用产物的时间**（如 `frontend/dist/index.html` 的 mtime），使用户能**自查**是否看到旧界面（缓解假阴性方向的静默问题）。
5. **有 Bun 时行为完全不变**（仍按判据决定构建/复用）。

## 涉及模块
- `start.bat`（`:backup` 之前的 `:frontend` / `:build_frontend` / `:bun_missing` 段）
- `docs/QUICKSTART.md`（若需同步说明"产物偏旧时仍会启动"）
- 可能涉及 `start.bat` 内新增一处标签（如 `:build_frontend_stale_nobun`）

## 不能破坏
- **产物缺失 + 无 Bun** 仍须明确失败并给安装指引（现状语义）。
- **有 Bun 时零变化**：构建判断、`bun install` / `bun run build` 调用、`:build_failed` 文案均不得改。
- 端口 8000、Ctrl+C、备份段、`SERVE_FRONTEND=1` / `LOCAL_ONLY_MODE=1`、各退出码语义不变。
- `start.bat` 保持 **CRLF**（LF-only = 0）与有效 UTF-8；无删除调用；不加依赖。
- 不引入构建指纹/新构建产物（那是更大的改动，已记 LATER）。

## 验收标准（可判定）
1. **无 Bun + 产物缺失** → 仍退出（非零），且输出含"未找到 Bun"与安装指引（与改造前一致）。
2. **无 Bun + 产物存在但过期** → **不再退出**，输出含"可能偏旧/将用现有产物启动"类警告，且**走到 `:launch`**（可用"把 Bun 探测指向不存在路径 + 把 `index.html` 的 mtime 调旧于 `package.json`"的方式实测）。
3. **无 Bun + 产物新鲜** → 行为不变（直接复用、走到 `:launch`）。
4. **有 Bun** → 产物新鲜时复用、过期时构建，`:build_failed` 文案不变。
5. 启动窗口**打印了所用产物的时间**。
6. 字节级：CRLF 完整（LF-only = 0）、UTF-8 严格解码通过、`git diff --check` 干净。

## 错误场景
- 产物存在但 `package.json` **不可读**（既有 `errorlevel 2` 分支 `:59-61`）→ **保持既有硬失败**（本卡不改该分支；它意味着安装损坏）。
- 产物存在但 `index.html` 为空/损坏 → 本卡不检测（超出范围）；不得因此新增阻塞。
- 无 Bun + 产物存在且过期 → 若**构建产物后**（有 Bun 的情况）失败，仍走 `:build_failed`。

## 测试要求
bat 无自动化测试框架，采用**实测**（沿用 VS-6/VS-8/VS-9 的夹具手法）：
- 造"无 Bun"场景：把探测两行替换为 `set "FQ_BUN="`；
- 三种输入组合各跑一次：**产物缺失** / **产物存在且过期** / **产物新鲜**；给出**原始输出**与退出码；
- 有 Bun 场景回归一次；
- 字节级校验 CRLF / UTF-8 / `git diff --check`。
- 临时文件放 `$env:TEMP`、用完送**回收站**；**注意**：用 PowerShell 读 `start.bat` 必须显式指定 UTF-8（PS 5.1 默认 ANSI 会损坏中文）。
由独立 Evaluator 复核"过期但无 Bun 时是否真的不再退出"与"有 Bun 时零变化"。
