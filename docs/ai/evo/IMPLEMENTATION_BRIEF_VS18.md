# IMPLEMENTATION_BRIEF — Vertical Slice 18：让"残缺件"不可能被误认为可用备份（P1 数据丢失）

> Orchestrator 第五阶段产物，2026-09-11。来源：**R4 审计 D4 的 P1**（`RELIABILITY_REPORT_R4.md`），**编排者已核实其两条前提**。

## 目标
用户在**数据受损、正按文档抢救**时，**不能**把被中断的半成品（`.partial`）当成可用备份覆盖回去。

## 用户场景
磁盘故障或误操作后，用户打开 `docs/QUICKSTART.md` 按"如何恢复"操作。指引说"选一个最近、状态正常的备份文件"——而 `backend/data/backups/` 里**时间戳最新、名字最像备份**的那个文件，恰恰可能是**上次备份被中断留下的 `.partial`**（内容被截断、不可用）。用户把它覆盖到 `finquant.db` ⇒ **真数据丢失**。

## 当前问题（已核实）
1. **恢复指引从不提 `.partial`**：`docs/QUICKSTART.md:174` 只写"选一个最近、状态正常的备份文件"；`:176` 只教处理 `-wal/-shm`。（`QUICKSTART` 中 `PARTIAL`/`UNKNOWN` 的两处命中是**行情数据状态词**，与备份无关——编排者已核。）
2. **备份形态描述也没提**：`:169` 只描述 `finquant-backup-<时间>.db`，未说明"写入期间会先出现一个临时半成品"。
3. **残件不会被自动回收**：`start.bat:121` 的回收判据是 `Test-Path -LiteralPath $part`，而 `$part = $dest + '.' + $PID + '.partial'` 含**本次进程的 PID**（编排者已核）⇒ 上次中断留下的残件名字对不上，**永不被后续运行清理**。
4. **回收失败会变成终止错误**：`:121` 里的三处 `DeleteFile(..., 'SendToRecycleBin')` **没有 `try/catch`**，而该载荷以 `$ErrorActionPreference='Stop'` 开头 ⇒ 在**无回收站的卷**（如某些网络盘/精简系统）上，回收动作会抛**终止错误**。
   - ⚠️ **诚实边界**：D4 标注本机 `backend\data\backups` 不存在，以上属**代码路径推演**；本卡要求实测（见下）。

## 理想行为
1. **`QUICKSTART.md` 的恢复步骤显式限定**：只选 **`finquant-backup-*.db`**，**不要用任何以 `.partial` 结尾的文件**；并**说明理由**——那是备份**尚未改名完成**的临时件。**⚠️ 准确表述（见下方「N1 更正」）**：**其内容可能完整、也可能残缺，无法从名字判断 ⇒ 一律不作为恢复来源**。**不得**写成"它一定不完整"（用户可能因此丢弃一份其实完好的库）。
2. **`QUICKSTART.md:169` 的备份描述补一句**：备份过程中会先出现一个临时文件（`.db.<数字>.partial`），**校验通过并改名后才成为正式备份**；看到它属正常现象、**请勿把它当作可恢复的备份**（内容是否完整无法从名字判断）。可在确认没有备份正在运行时，按习惯移走或送回收站。
3. **`start.bat:121` 的三处回收动作加 `try/catch`**：回收失败**不得**让整个备份流程以终止错误收场、也不得改变既有退出码语义。
   - **⚠️ 收益已窄化（见下方「N3 更正」）**：独立评估者逐条追踪三处调用点后确认——**它们都位于"结局已是 `:backup_failed`"的路径上**，故**不存在"把成功备份误报为失败"**的路径。加 `try/catch` 仍**无害且更稳**（避免回收失败把流程直接打断），但**结果文件须如实写成"窄化后的收益"**，不得照抄"会终止错误"这类更强的说法。
4. **（N2）遗留提示的匹配放宽**：新增的遗留 `.partial` 提示应改用 **`-Filter 'finquant-backup-*.partial*'`**，使 `.partial` 的**伴生件**（`-journal`/`-shm`/`-wal`）也能被提示到——它们对现有两条 `-Filter` 都不可见、会**静默累积**。**注意**：**7 份「有效备份」计数必须仍用 `'finquant-backup-*.db'` 不变**（放宽一处、锁住另一处）。

## ⚠️ N1 更正（来自 VS-17 独立评估者的实测，推翻本卡初稿的一处依据）
评估者用独占写 + 紧轮询**在"校验期"打断备份**，实测：该 `.partial` 残件与两份 `integrity_check='ok'` 的有效备份在**大小与 sha256 上完全相同**。
⇒ **`.partial` 后缀只保证"尚未改名"，不保证"内容残缺"**：它**可能完整可用**，也可能残缺。
⇒ 文案**必须**落在"**无法从名字判断 ⇒ 一律不作为恢复来源**"这一中性表述上（即项目原则"宁可说未知，也不要把故障说过头"的直接应用）。本卡初稿"内容可能不完整"的说法**已作废**。

## ⚠️ N3 更正（同上来源，收窄本卡第 3 项的收益）
三处 `DeleteFile` 调用点经独立追踪**均在"结局已是 `:backup_failed`"的路径上** ⇒ **不会把成功备份误报为失败**（D4 原文的严重性被高估）。`try/catch` 保留，但按"窄化后的收益"表述。

## 涉及模块
- `docs/QUICKSTART.md`（仅恢复段 `:169`/`:174` 附近）
- `start.bat`（仅 `:121` 载荷内的回收动作）

## 不能破坏
- **快照仍是 `sqlite3.Connection.backup()` + `PRAGMA integrity_check`**；**不得退回"只复制 finquant.db"**。
- **失败只回收自己的 `.partial`、绝不触碰任何 `.db`**（VS-17 的核心成果，`DeleteFile($dest` 必须仍为 **0** 次）。
- 7 份 `-Filter 'finquant-backup-*.db'` 计数、遗留 `.partial` 提示、`:118/:119/:122` 三条分支、"失败不阻塞启动"（`:backup_failed` 仍 `goto launch`）。
- **`:120-121` 的两条承重属性**：`:121` 行首**保留 2 个前导空格**、trim 后**首末字符码均为 34（`"`）**。改动时**逐字**处理这两行。
- `start.bat` 保持 CRLF/严格 UTF-8；不删文件（一律回收站）；不 commit。

## 验收标准（可判定）
1. `QUICKSTART.md` 恢复步骤中出现**明确的选取限定**（`finquant-backup-*.db`）与**对 `.partial` 的排除说明**（含"为什么"）；`:169` 解释了 `.partial` 的来源。
2. `start.bat` 中三处回收动作均在 `try/catch` 内；**正常路径与失败路径的行为不变**（仍产出最终 `.db`；失败仍只回收自己的 `.partial`、仍 `exit 1` → `:backup_failed`）。
3. **回收失败不再终止**：给出实测——构造"回收动作抛错"的情形（例如让目标无法送回收站，或用一个**隔离的最小 PowerShell 探针**证明"`$ErrorActionPreference='Stop'` 下，`try{ DeleteFile(...) }catch{...}` 不终止、而裸调用会终止"），并说明本卡的做法是哪种。
4. **残件确实不会被自动回收**：用夹具实测——先留一个**名字含其他 PID** 的 `.partial`，跑一次正常备份，断言该残件**仍在**（印证"用户必须自己处理"这一前提，也是文案这么写的依据）。
5. `DeleteFile($dest` 仍为 **0** 次；`:121` 前导空格=2、首末字符码=34。
6. 字节级：`start.bat` CRLF 完整（LF-only=0）、严格 UTF-8、`git diff --check` 干净。

## 错误场景
- 回收失败（无回收站/权限）：备份流程**继续**，最终仍按原语义返回（成功 0 / 失败 1）。
- 用户已在别的窗口删掉了自己的 `.partial`：`Test-Path` 为假 ⇒ 不报错。
- `docs/QUICKSTART.md` 的措辞**不得**让用户以为"看到 `.partial` 就是备份失败"——它是**过程产物**；真正失败仍表现为启动窗口的备份提示。
