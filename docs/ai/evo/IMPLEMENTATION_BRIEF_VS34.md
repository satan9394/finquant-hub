# IMPLEMENTATION_BRIEF — VS-34：Chat 的静默吞错改为可归因、可重试（O2）

> 来源：**两个独立来源指向同一处**——VS-25 的实现者报备 `frontend/src/pages/Chat.tsx:119-127`（喂 Chat 角色选择器的 `.catch(()=>{})`）与 VS-32 的评估者报备 `Chat.tsx:176-179`（详情消息读取 `.catch(() => {})`）。与 VS-25 修的是**同一类缺陷、不同位置**。

## 目标
Chat 里**读取失败被静默吞掉**：用户看不到失败、也没有重试入口。

## 第一步（**先做，再改**）
**先核实现状**：把 `Chat.tsx` 里**所有** `.catch(() => {})` / 吞掉错误的分支列出来（文件:行 + 它喂的是什么 UI），并在结果文件里给出清单。**若某处其实是"有意为之且无害"（例如可选的、失败即降级的装饰性拉取），请说明并列出理由**——**本卡不要求你把每一处都改**，要求的是**每处都有明确归因**。

## 理想行为（对确实需要改的那些）
对齐 **VS-25 已确立的范式**（`Discussion.tsx` 的 `loadAgents`：成功/失败分开、请求序号丢弃过期响应、**失败时不清失败态**、失败处复用 `LoadFailureAlert` 并提供**真会重发请求**的重试）：
1. 失败**可归因**（有底层原因，不是"没反应"）；
2. 有**可点击的重试**，且重试**真的重新发起请求**；
3. 失败**不得**被渲染成"空"（**这是 VS-19/VS-22 反复确立的底线**）。

## 不能破坏
- **VS-23/VS-28 的 chat 截断信号**（`done.truncated_by_deadline` 与 `ChatMessageBubble` 的持久警示条，`3109b6e` 已验收）——**不要动那条链路**；
- **VS-29 的三态契约**（`LoadFailureAlert.tsx` 是族内唯一实现处，`8d05556` 已验收）——**优先复用，不要另造三态判定**；
- Chat 既有流式/深链/AuthUnavailable 等测试全绿；既有断言**不得放宽**；不加依赖；**不 commit**。

## 验收标准
1. **清单**：`Chat.tsx` 内所有吞错点逐处归因（改/不改 + 理由）；
2. **失败可见**：构造读取失败 ⇒ 断言出现错误态 + 底层原因 + 可点重试；
3. **重试真重发**：以**请求计数**证明（如 n=1 → n=2），**不要只断言"重试后成功"**；
4. **失败不伪装成空**：断言失败态下**不出现**空态文案；
5. **零回归**：Chat 既有测试全绿；
6. **鉴别力证明**：副本里把修复退回 ⇒ 至少一条新用例变红（贴原始输出）；
7. 门禁：相关 vitest + **串行** `bun run build`。
