## 冲突检测与裁决

- **A 说"无 P0" vs D 的 P0/P1**：A 从首次成功使用角度无 P0（文档齐全、路径走通）；D 从故障假设角度提出数据/资源风险。**裁决**：无备份恢复=数据丢失风险（对本地个人应用真实存在）但按定义"阻碍核心使用/严重安全"勉强，**定 P1**；调度无限重试+失败报告伪装成功=数据质量+资源风险，**定 P1**（不阻碍首次使用但持续恶化成熟度）。
- **A 的"500 无错误 ID" 与 D 的"报告 completed 全失败文本"同主题**（失败可观测性/诚实性）→ 合并为一条缺口 G-06。
- **B 的"IR→代码→回测闭环" 与 A 的"Alpha 无入口"**：后者是纯导航发现（成本低），前者是能力增强（成本高）→ 拆两条，分不同优先级。

## 缺口图（去重后，按优先级）

### P1（明显破坏核心体验 / 数据风险）
- **G-01 无备份/恢复路径**：《D》。证据：database.py:1854-2019（.bak 只迁移留、不清理）、start.bat 无备份步骤。用户数据（组合/研报/记忆）磁盘故障或升级失败后不可恢复。建议：start.bat 启动前自动备份 + 文档化恢复；清理过期 .bak。
- **G-02 调度任务失败无限重试**：《D》。证据：scheduler.py:384-398 + research_jobs.py:131-225（status='failed' 无条件 attempt+1，每 30s）。持续失败（无效 key）→ 无限烧 API + DB 膨胀。建议：max_attempts + 指数退避 + 失败挂起 UI 提示。
- **G-03 报告伪装成功**：《D》 research_orch.py:223-225 + research.py:274-283：LLM 失败时 agent 只降级为"【分析失败】"文本，done 照发→报告标 completed。用户拿到全是失败文本的"成功报告"。建议：any agent 失败或 lead 失败 → quality=PARTIAL/FAILED + done 事件携带质量元数据 + UI 诚实提示。
- **G-04 站内零引导无帮助入口**：《A》。非技术用户首次打开只有 Dashboard，无站内帮助/FAQ/文档链接、无首启引导。建议：首启引导卡（3 步）+ 站内帮助/文档入口。
- **G-05 AI 首次配置双路径（.env 手编陷阱 + UI 凭据重启失效）**：《A》 QUICKSTART.md:63-70 + start.bat:86。建议：主推 UI 配置路径并解决 MASTER_KEY 持久化语义，或首配置向导。
- **G-06 失败可观测性差（500 无 ID + 报告质量不透明）**：《A》《D》。建议：500 响应带错误 ID + 日志关联；报告内容 quality 指标展示。

### P2（显著提升成熟度）
- **G-07 MarketDataService 单例绕过 8 处（熔断失效+冷连）**：《C》。工具/编排器每次 new 实例 → 熔断状态丢失、httpx 每次重建。建议：工具注入单例或 CircuitBreaker 模块级共享。
- **G-08 database.py 上帝模块+迁移样板重复**：《C》。建议：拆 schema 目录 + 迁移注册表（长期）。
- **G-09 _OWNER_TABLES 手工清单**：《C》。建议：新表迁移模板自动对照 + 测试断言 owner guard 存在。
- **G-10 加市场数据源成本高**：《C》 6+ 处硬编码。长期路线图已有 DataProvider 协议，未做。
- **G-11 LLM 调用无重试**：《D》。单次抖动致整轮失败。建议：5xx/429 重试 2 次指数退避。
- **G-12 cron 并发无上限**：《D》。due jobs gather 无 semaphore。建议：复用 SCHEDULER_CONCURRENCY。
- **G-13 Alpha 研究无导航入口（功能不可发现）**：《A》。仅 /alpha 隐式路由。
- **G-14 无 CI**：《C》。809+470+E2E 全本地手工。
- **G-15 用量计价借鉴 one-api/NewAPI 模型（B 的纠偏）**：《B》。可选增强。
