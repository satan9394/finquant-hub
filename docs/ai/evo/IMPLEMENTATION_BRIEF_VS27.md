# IMPLEMENTATION_BRIEF — Vertical Slice 27：研究编排的整轮等待必须有上界，且截断必须"看得见"

> Orchestrator 第五阶段产物。来源：**R5 审计 D5 的最高危项**（`RELIABILITY_REPORT_R5.md`），编排者列为 **NOW-3**，其关键事实**已由编排者逐条 grep 核实**。

## 目标
让"**深度研究**"这条**产品核心路径**的整轮等待**有上界**，并且当上界触发时，**用户看得到、档案记得下**。

## 用户场景
用户点"深度研究"，去泡杯咖啡。若上游某次调用持续超时/重试，他可能**等 60 分钟**，**没有任何取消按钮**，**界面也不会告诉他"已经提前结束"**——他会以为还在跑，或以为程序卡死。

## 当前问题（**编排者已核实，逐条给事实**）
- VS-21/23 的整轮上界**只覆盖交互 chat**：全 backend 中 `deadline_seconds` **仅**出现在 `chat.py`(2 处) 与 `llm_client.py`(18 处)。
- **研究走的是另一条循环**：`backend/app/services/research_orch.py:260` 的 `for _round in range(5)`，并在 `:292` 收尾再调一次 ⇒ **6 次 LLM 调用/Agent**；链路 `_request_tool_round`（`:181-199`）→ `chat_with_tools_safe`，**全都不传 `deadline_seconds`**（该文件零命中）。
- 单次上限约 **300s**（`total_budget_seconds` 默认 180 + 单次尝试超时 120）⇒ **单 Agent 最坏 ~1800s**；主编（team-lead）再串行一次 ⇒ **整轮最坏约 60 分钟**。
- **无产品内取消**；该次运行的 `done`/落库结果里**没有截断信号**。
- **D5 的原话值得抄在卡上**："这正是 VS-21 注释自己算过的 5×(180+120) 场景，却只接到了最便宜的路径。"

## 理想行为（**第 3 条是本卡的灵魂，别漏**）
1. **整轮有上界**：把运行级截止时间**向下传到每个 Agent 的每次调用**（沿用 `chat_with_tools_safe(..., deadline_seconds=…)` 的既有机制），使整轮墙钟有可判定的上界。
2. **触发时给部分结果而非抛掉一切**：已经完成的 Agent 成果必须保留（本仓既有原则：**局部失败不得说成整轮失败**）。
3. **截断必须"看得见"，且信号必须有真实消费方**——⚠️ **反面教材（必须避免重犯）**：VS-23 给 chat 加了 `done.truncated_by_deadline`，但 **D5 核实该字段在 frontend 全库零消费方**，且 `tool_loop_truncated` 被 `chat.py:179` 的白名单丢弃 ⇒ **"三通道实为一通道，用户只看到正文前缀"**。**本卡新增的任何截断信号，都必须能指出"谁消费它、用户在哪里看到"**；**若答案只是"字段存在"，则不算实现完成**。
4. 该信号须与**落库内容同源**（用户所见 == 已保存内容）。

- 相关测试

## 不能破坏
- **VS-20 的结构化状态契约**：`agent_results[key].status`（`completed`/`degraded`/`failed`）+ `error`/`degraded_reasons`；**不得**退回字符串哨兵判据。
- 4 个 Agent 的**并行**语义与既有轮数上限语义（`max_rounds=5`）。
- `chat_with_tools_loop` / `chat_with_tools_safe` 的既有公开签名契约（VS-23 已定：`deadline_seconds` 为**末尾 keyword-only、默认 None**；`None` ⇒ **逐项零回归**）。
- 不加依赖、不改 schema；不删文件；**不 commit**。

## 验收标准（可判定）
1. **上界可判定**：用**假时钟**实测——给定运行级截止 D 与 N 个 Agent，整轮墙钟 ≤ 一个**写明公式**的上界（请把公式与"只在轮间检查"这一前提写进 docstring）；并断言**无任何调用在截止之后才发起**。
2. **部分结果保留**：截止触发后，已完成的 Agent 结果**仍在**最终报告里，且状态**如实**（该 Agent `degraded` 或 `failed` + 原因，不得静默变 `completed`）。
3. **信号有真实消费方**：明确指出**消费方位置**（`文件:行` 或用户可见文案），并给出**实测**（SSE/接口响应或界面断言）；**若无法展示，则必须在结果文件里论证并写明"仅落库、不展示"的理由**。
4. **同源**：用户所见与落库内容一致（给出断言）。
5. **零回归**：不传截止时**逐项与现状一致**；既有 `research_orch` 与 `llm_client` 测试全绿。
6. **鉴别力证明**：从**副本**去掉截止判断 ⇒ 至少一条新用例变红（贴原始输出）。
7. 门禁：相关 pytest 聚焦文件 + `ruff check .`（**不要跑全量 pytest，也不要跑 `tests/test_api.py`——本机会挂**）。

## 错误场景
- 截止**恰在一次成功调用之后**才越界 ⇒ 按**正常完成**处理，**不得**误报截断（VS-23 已有此边界用例，可参照）。
- 截止在**首轮之前**就已过 ⇒ **不得发起任何 LLM 调用**，直接产出"未开始即已超时"的如实结果。
- 截止值非法（0/负/NaN/Inf）⇒ 明确拒绝（`ValueError`），与 VS-21/23 的既有约定一致。

## 测试要求
- 用**假时钟**做上界与边界断言（本仓既有做法），**不要**用真实 sleep 拖慢门禁。
- 临时/变异文件放 `$env:TEMP`；**不要把门禁输出写进仓库目录**；做变异/还原验证**先声明窗口**。
- 由独立 Evaluator 复核：①上界公式与实测一致；②**信号是否真有消费方**（这是本卡最容易被"加了字段就算完成"糊弄过去的地方）；③不传截止时零回归。
