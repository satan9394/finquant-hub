# IMPLEMENTATION_BRIEF — Vertical Slice 25：AI 讨论首用不得"静默死胡同"

> Orchestrator 第五阶段产物。来源：**R5 审计 A5 的 P2-3**（`PRODUCT_UX_REPORT_R5.md`），编排者列为 **NOW-2**。

## 目标
用户第一次尝试"多 Agent 讨论"时，**不得**在没有任何归因的情况下**被挡在一个做不成的提示上**。

## 用户场景
非技术用户打开讨论页 → 选角色 → 点开始。若"可用角色"这一次请求失败，界面**既不说失败、也不给重试**，只在用户选不够时挡一句"**请至少选择 3 个角色**"。用户按提示也做不成，且**永远不知道是网络/权限/服务的问题**。

## 当前问题（A5 已核码）
- `frontend/src/pages/Discussion.tsx:94`：`apiClient.get('/agents').catch(() => {})` —— **静默吞错**。
- 角色下拉（约 `:380`）的**全部选项**来自该请求。
- `Discussion.tsx:142`：用"**请至少选择 3 个角色**"挡人 ⇒ 请求失败时用户被**误导**为"自己选得不够"。
- **同类先例**：R3 曾找出"本地模式登录死胡同"（已修）——本卡是同一类。

## 理想行为
1. 该请求失败 ⇒ **可见的错误态**（错误文案 + **具体原因** + **可点重试**），**复用现有 `frontend/src/components/LoadFailureAlert.tsx`**（VS-22 已建，**不要另写一套**）。
2. **重试真的重新发起**该请求；恢复成功后错误态消失、下拉可选。
3. **不得**在请求失败时仍把"请至少选择 3 个角色"作为**唯一**解释——那正是本卡要消除的误导。
4. 请求成功但**返回的可用角色本身少于 3 个** ⇒ 如实说明（如"当前仅 N 个角色可用"），**不要**让用户对着不可能达成的提示反复尝试。

## 涉及模块
- `frontend/src/pages/Discussion.tsx`（主要）
- `frontend/src/i18n/{zh,en}.ts`（新增键须**双写**）
- 复用 `frontend/src/components/LoadFailureAlert.tsx`
- 相关测试

## 不能破坏
- 请求成功时的既有选择/开始流程与既有测试；
- `LoadFailureAlert` 的既有契约与既有调用点（Chat/Discussion 左栏、首页研究运行区块）；
- i18n **zh/en 键集合一致**（当前各 2478 键，改后仍须一致且无重复）；
- 不加依赖、不改后端、不改 schema；不删文件；**不 commit**。

## 验收标准（可判定）
1. **失败可归因**：mock 该请求失败 ⇒ 原位出现 `LoadFailureAlert`（失败文案 + 具体错误 + 重试），且**"请至少选择 3 个角色"不再是唯一解释**。
2. **重试真重发**：以请求计数证明（1→2→3）；恢复成功 ⇒ 错误态消失、选项可用。
3. **角色不足 3 个**时给出如实说明（构造"仅 1 个角色"的夹具）。
4. **成功路径零回归**：既有讨论流程测试全绿。
5. **鉴别力证明**：把新增的错误分支/重试接线从**副本**去掉后，至少一条新用例变红（贴原始输出）。
6. 门禁：相关 vitest 全绿 + **串行** `bun run build`（含 `tsc -b`）。

## 错误场景
- 请求超时 / 401 / 500 ⇒ 均走同一条可见错误路径（**不要**只处理其中一种）。
- 请求成功但返回空数组 ⇒ 与"少于 3 个"同处理，**不得**崩溃。
