## 问题一：模型管理模块（供应商配置体验差）

### 用户实测反馈（原话要点）
1. **Endpoint/请求 URL 混乱**："我填的是请求 URL，但那里显示的 Endpoint 并不是请求 URL，不知道具体是什么"——用户期望填**完整的 API 请求地址**（如 `https://api.openai.com/v1`），但字段语义/显示与请求 URL 不一致。
2. **API Key 环境变量**："为什么要填整个 API Key 的环境变量？这是什么意思？"——用户期望**直接填一个 API Key 值**即可，不理解"环境变量名"概念。
3. **模型列表拉取缺失**："每个请求 URL 都应该能返回模型列表，但你没做到"——期望配置后能自动拉取/选择该端点可用模型。
4. **测试报错**：自测 OpenAI 供应商报 "API 返回 404：<!DOCTYPE html>..."——404 是 HTML 而非 JSON，指向 **URL 拼接错误**（base_url 被二次拼接成 `/chat/completions/chat/completions` 或类似）。

### 当前代码根因（2026-09-07 核实）
- `backend/app/models.py`：`ModelConfigIn` 字段 `name/provider/base_url/model_name/api_key_env/temperature/max_tokens`——**存的是 `api_key_env`（环境变量名）而非 key 值**；`base_url` 无"是 base 还是完整 endpoint"的明确契约。
- `backend/app/services/llm_client.py:86/117/164`：`url = f"{self.base_url}/chat/completions"`——**若用户填完整 endpoint 会被二次拼接**；且 `self.base_url = base_url.rstrip("/")` 只去尾斜杠。
- `backend/app/services/model_router.py:38-43`：`api_key = os.getenv(cfg["api_key_env"])`——**从环境变量读 key**，用户填的"环境变量名"无对应 env 时 LLMError"未配置 API Key"。
- `backend/app/database.py`：`model_configs` 表 `api_key_env TEXT` 列（存变量名不存值）。
- 无"列出该端点可用模型"端点（不自省 `/v1/models`）。
- 前端 `frontend/src/pages/Models.tsx` + 相关表单：字段展示与上述后端一致（Endpoint 字段、API Key 环境变量输入框）。

### 参考经验：CC Switch（github.com/farion1231/cc-switch）
（2026-09-07 检索，成熟的开源"多工具供应商管理"实现，MIT）
- **供应商 = 预设/名称 + Base URL + API Key 值** 三元组；用户只填三者，**key 填值不填环境变量名**。
- **密钥本地存储**：SQLite（`~/.cc-switch/cc-switch.db`）统一存供应商/MCP/配置，密钥随供应商记录走，**不依赖 .env/环境变量**；原子写入防损坏。
- **50+ 供应商预设**：内置各厂 base_url 惯例（OpenAI/Anthropic/DeepSeek/中转等），一键导入。
- **模型列表/能力目录**：部分工具带模型目录/能力清单（如 Pi 57 模型目录），端点可自省时拉取。
- **Full URL Endpoint Mode**：高级选项允许把 base_url 当完整端点（正是本项目要解决的二义性——CC Switch 显式区分"base_url"与"完整 endpoint"两种模式）。
- **测试/延迟**：SpeedtestService 测 API 端点延迟，供应商健康监控。
- 关键设计启示：①字段语义必须用户可懂（Base URL 或完整 Endpoint 二选一明确标注）②key 填值本地存 ③配置可一键测通 ④错误给可行动中文提示。

### 建议重构方向（供 Codex 实施，边界可按 Codex 拆卡）
1. `model_configs` 表/schema：`api_key_env` → **`api_key`（存加密 key 值）**（本地单用户可简单加密或明文 SQLite；参考项目已有 Fernet credential_store，可复用加密凭据表模式——见 `backend/app/services/credential_store.py` 既有"加密凭据"基建）；保留 `api_key_env` 作**可选**兼容（两模式：直接填 key 或引用 env 名）。
2. **URL 契约**：明确 `base_url` 语义为 **base（如 https://api.openai.com/v1）**，llm_client 拼 `/chat/completions`；或给用户"完整 Endpoint"选项并在请求时**不再二次拼接**（探测结尾是否已是 /chat/completions）。表单文案改为用户能懂："API 地址（如 https://api.openai.com/v1）"。
3. **模型列表拉取**：新增端点（或测试端点扩展）`GET {base_url}/models`（OpenAI 兼容）→ 返回可选模型供用户选，失败给诚实提示"该端点不支持列出模型，请手动填模型名"。
4. **测试报告**：`POST /{id}/test` 失败时返回**响应体片段**（而非只 404/超时），前端展示可行动错误（"地址可能被重复拼接，当前请求了 xxx"）。
5. 前端 Models.tsx 表单重排：名称/供应商预设(可选)/API 地址/API Key(直接填)/模型名(带"拉取列表"按钮)/温度——非技术用户可完成。

## 问题二：机会发现（Discover）模块空态 + 术语外行难懂

### 用户实测反馈（原话要点）
1. **空态无推荐**："描述你想找的公司相关字段（股票结果、因子等）全是空的，没有任何推荐"——无输入时页面空荡，无从选择。
2. **不支持自然语言**："用户不一定记得股票代码，应允许自然语言描述找公司"。
3. **行业分类不全**："细分行业里缺按行业分类/概念股归类"。
4. **术语外行看不懂（重点）**："跌涨停我看不懂，封单额是什么？涨停统计是什么？我是外行都看不懂"——**涨停池/跌停池页的专业术语对非技术用户无解释**。

### 建议方向
1. 空态默认推荐：无输入时展示"今日热门/示例公司/按板块推荐"（随机或按前一交易日反馈），页面不空。
2. 自然语言搜索：已有 `/api/market/search`（名称/拼音）与全局入口，Discover 明确"可输公司名/描述"。
3. 行业/概念分类：加标签体系（行业/概念股）便于浏览。
4. **术语中文化 + 悬停解释（关键）**：涨停池页每个专业列（封单额/涨停统计/连板/炸板 等）加中文释义 tooltip/问号；或列名直接改外行可懂（封单额→"排队买入的资金量"）。参考知识库 INDICATOR_KNOWLEDGE 的解释卡模式（`frontend/src/features/indicatorKnowledge.ts`——已有"用途/读法/误区"卡片范式可复用）。
5. "跌停池/涨停池"入口本身对新手要解释（什么是涨停/为什么看）。

## 问题三：导航冗余（研究模式三入口）+"研究模式"困惑

### 用户实测反馈
"左上角有'研究模式'（快速分析/深度研究等），既然已有'研究'模块和'研究工作区'，为什么右上角还提供这三种？多余、体验差。"

### 现状（2026-09-07 核实）
- 侧栏/顶栏有"研究模式"下拉（Fast/Deep/Review/Thesis 等，可能来自 `frontend/src/pages/Research.tsx` 的 ResearchModeSelector 或类似）。
- 与独立"研究工作区"（/research/:symbol，BACKLOG-032 后的连续工作面）职责重叠。
- BACKLOG-032 已收敛全局提问入口为单 ⌘K + hero 弹窗，但"研究模式"选择器仍暴露多重入口。

### 建议方向
- 合并/收敛：把"快速分析/深度研究/Review/Thesis"统一为研究页内的**模式切换**（进入研究后选深度），而非顶栏独立入口；或按用户动作语境只显示相关模式。目标：**任一时刻只有一个主入口 + 明确下一步**。可参考 Astra 审查 B12 方案①"连续工作面：提交→选对象→选深度"的收口思路（已在 032 部分落地）。
